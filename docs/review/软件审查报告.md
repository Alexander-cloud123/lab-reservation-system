## 三、问题清单（按严重级别）

### 🔴 高（2 项，必须修）

**H1 过期 Token 仍被鉴权放行（安全缺陷）**
- 定位：`AuthInterceptor.java:75-79`、`JwtUtil.java:46-52`（生成时设置 exp：`JwtUtil.java:33-40`，但校验只验签名）
- 证据：`jwt.setKey(secret).verify()` 仅校验签名；Hutool 的 `verify()` 不校验 `exp`，需 `validate()`/`validate(Date)` 才检查过期。动态复现：过期 1 小时的合法 Token 访问 `/api/user/info` 返回 200。
- 影响：泄漏/离线的 Token 永不过期；"修改密码后需重新登录"的机制也形同虚设（旧 Token 仍可继续使用）。
- 修复建议：`parseAndVerify`/`parseToken` 在 `verify()` 后追加过期校验（校验 `exp` claim 或调用 `jwt.validate(Date leeway)`），不通过统一抛 401。

**H2 审核通过时不复查冲突，可产生"双已通过"（核心业务逻辑缺陷）**
- 定位：`ReservationServiceImpl.java:218`（auditReservation）、`:247`（batchAudit）
- 证据：冲突检测仅在提交时与「已通过」预约比较（`:88-91`）；两个重叠的待审核先后被通过时均不复查 → 动态复现两条均变已通过。
- 影响：同一教室同一时段出现两个已通过预约，直接违反"禁止冲突预约"核心规则，答辩时被追问核心逻辑风险高。
- 修复建议：审核为「通过」时，对该预约再次执行冲突检测（同教室同日、status=1、排除自身、重叠公式），冲突则拒绝并提示；批量审核逐条校验，冲突行跳过并统计。

### 🟠 中（4 项，建议修）

**M1 允许预约过去日期**
- 定位：`ReservationServiceImpl.java:122-142`（createReservation 未校验 `reserveDate` 是否早于今天）
- 证据：动态复现 2020-01-01 预约成功创建。
- 影响：脏数据；日历/看板统计口径被污染。
- 修复建议：`reserveDate.isBefore(LocalDate.now())` 抛业务异常（口径与前端 disabled-date 一致：允许今天及以后）。

**M2 预约提交存在并发竞态（无锁/无唯一约束兜底）**
- 定位：`ReservationServiceImpl.java:88-91`（先查后插）；`init_db.sql:73` `idx_class_date(classroom_id, reserve_date)` 为非唯一索引
- 证据：check-conflict 与 insert 之间无事务锁，也无 (classroom_id, reserve_date, start_time, end_time) 唯一约束；两个并发请求可同时通过检测并双写成功。
- 影响：极端并发下出现重复占用；当前实训规模概率低，属理论风险。
- 修复建议（按成本排序）：① 对同教室同日加 `SELECT … FOR UPDATE` 行锁（@Transactional 包裹 check+insert）；② 增加唯一索引并捕获 `DuplicateKeyException` 返回友好提示；③ 乐观锁版本号。

**M3 AI 推荐接口信任请求体 userId，可越权读取他人预约偏好（AI 开启态触发）**
- 定位：`AiController.java:54-56`（`recommend(@RequestBody …request)` 直接取 `request.getUserId()`）→ `AiRecommendServiceImpl.java:80-95`（按该 userId 查历史偏好）
- 证据：任意登录用户可传他人 userId，获取其历史预约习惯生成的推荐（楼栋/时段/容量偏好数据）。
- 影响：个人数据越权读取（仅偏好统计，无敏感字段），但属越权缺陷。
- 修复建议：改为 `UserContext.getUserId()`（与 chat/parse 一致），入参 userId 仅作可选覆盖或删除。

**M4 禁用账号后已签发 Token 仍可访问（状态校验仅登录时执行）**
- 定位：`UserServiceImpl.java:65-66`（登录时校验 status）vs `AuthInterceptor.java:54-63`（拦截器只验签名与角色，不查用户状态）
- 证据：禁用用户现有 Token 在 24 小时有效期内仍可正常调用接口。
- 影响："禁用账号"不立即生效，管理员操作预期落空。
- 修复建议：拦截器内对写操作/高频接口查一次用户状态（或精简方案：把 token 有效期缩短 + 关键接口校验状态）。
