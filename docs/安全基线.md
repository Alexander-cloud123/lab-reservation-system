# 安全基线

面向「可公开展示 / 可上线」的最小安全闭包：只收敛部署配置与网关行为，不改业务规则、不加依赖、不动表结构。所有结论都可用 `server/scripts/security-check.ps1` 与 `docker compose` 复现。

---

## 1. 为什么做这一轮

需求文档 §1.5 已写明「密钥仅后端、权限拦截、参数校验」等非功能要求，代码侧基本落实（BCrypt、拦截器、`token_version` 撤销、Redis 失败锁定）。真正的缺口在**部署口径**：

| 缺口 | 现状（加固前） | 后果 |
|------|----------------|------|
| JWT 密钥 | compose 使用 `${JWT_SECRET:-reservation-system-jwt-secret-2026}`，且未激活非开发 profile，`JwtSecretGuard` 直接放行 | 仓库里公开的默认密钥可被用来伪造 admin Token（无状态模式 `REDIS_ENABLE=false` 下实测直接放行；Redis 启用时另被会话校验挡住，但默认密钥本身仍是缺陷） |
| 接口文档 | `knife4j.enable` 默认 `true`，compose 未关闭 | 公网可浏览 `/doc.html`，接口结构全暴露 |
| 跨域 | `app.cors.allowed-origins` 写死 `*` 且 `allowCredentials(true)` | 任意站点可发起带凭据请求（纵深防御缺口） |
| 网关 | 无安全响应头、无限流、暴露 nginx 版本 | 缺少点击劫持 / MIME 嗅探防护；登录、注册可被批量撞库 |
| 日志 | 容器内 MyBatis `StdOutImpl` 逐条打印 SQL | 生产日志噪声与参数泄露面 |

## 2. 加固内容

### 2.1 compose 按生产口径启动（`docker-compose.yml`）

```yaml
SPRING_PROFILES_ACTIVE: prod
JWT_SECRET: ${JWT_SECRET:?JWT_SECRET 未设置：请先 cp .env.example .env ...}
KNIFE4J_ENABLE: "false"
MYBATIS_LOG_IMPL: org.apache.ibatis.logging.nologging.NoLoggingImpl
CORS_ALLOWED_ORIGINS: "http://127.0.0.1:${WEB_PORT:-8088},http://localhost:${WEB_PORT:-8088},http://127.0.0.1:5173,http://localhost:5173"
```

- `prod` 激活 `JwtSecretGuard`：密钥为空、等于开发默认值、或不足 32 字节时**启动失败**，不会带病运行。
- `JWT_SECRET:?` 在变量缺失/为空时让 `docker compose` 在解析阶段就报错，错误文案直接给出修复命令。
- 文档双关闭：`knife4j.enable` 与 `springdoc.api-docs / swagger-ui` 共用 `KNIFE4J_ENABLE`；再叠一层 `spring.web.resources.add-mappings: ${KNIFE4J_ENABLE:true}`，因为 `doc.html` 是 classpath 静态资源，单靠 `knife4j.enable=false` 仍能被直接访问。关闭后两个路径都不再返回文档页 / OpenAPI JSON，落到统一 404 语义（`{"code":404,"message":"接口不存在"}`；HTTP 状态仍为 200，沿用项目「业务错误 200 + 响应体 code」约定）。

### 2.2 网关加固（`web/nginx.conf`）

- `server_tokens off`，`Server` 头只留 `nginx`。
- 响应头：`X-Content-Type-Options: nosniff`、`X-Frame-Options: SAMEORIGIN`、`Referrer-Policy: strict-origin-when-cross-origin`、`Permissions-Policy`（禁用摄像头/麦克风/定位）；`/assets/` 与 `/index.html` 因自带 `add_header Cache-Control` 会覆盖父级，已重复声明。
- 限流：`limit_req_zone` 分为 `auth_login_limit` 与 `auth_register_limit` 两个 10m 区（`rate=10r/m`），分别只作用于 `POST /api/user/login` 与 `POST /api/user/register`（`burst=9 nodelay`、`limit_req_status 429`）；两个接口互不消耗对方的额度，单接口第 11 次起 429。

> 为什么限流放 nginx 而不是后端：需求边界禁止引入新依赖（Bucket4j / Resilience4j），而按账号的失败锁定已由 `UserServiceImpl` + Redis 实现（5 次锁定 15 分钟）；网关层补的是「按 IP 防批量注册/撞库」，两套机制互补，互不替代。

## 3. 验证

```powershell
# 1. 缺少密钥时必须失败（先把 .env 挪走或用空变量）
$env:JWT_SECRET=''; docker compose config --quiet   # 退出码 1 + 中文提示

# 2. 正常启动
docker compose build api web
docker compose up -d
docker compose ps                                    # mysql/redis/api/web 均 healthy

# 3. 一键自检（8 项）
pwsh server/scripts/security-check.ps1
```

自检项与加固前实测结果：

| # | 检查项 | 加固前 | 加固后 |
|---|--------|--------|--------|
| 1 | 前端安全响应头齐全 | FAIL（无任何安全头；配置核对） | PASS |
| 2 | `Server` 不泄露 nginx 版本 | FAIL（`nginx/1.27.x`；配置核对） | PASS（`nginx`） |
| 3 | `/doc.html` 不可访问 | FAIL（200，返回 Knife4j 页面） | PASS（统一 404 语义，无文档内容） |
| 4 | `/v3/api-docs` 不可访问 | FAIL（200，返回 OpenAPI JSON） | PASS（统一 404 语义，无 schema） |
| 5 | 默认密钥伪造 admin Token 被拒 | FAIL（`REDIS_ENABLE=false` 时 200，见下） | PASS（401，签名即拒） |
| 6 | 未登录访问受保护接口 | PASS（401） | PASS（401） |
| 7 | 学生 Token 调管理员接口 | PASS（403） | PASS（403） |
| 8 | 登录/注册限流（第 11 次 429） | FAIL（无限流；配置核对） | PASS |

第 3 / 4 / 5 项的「加固前」是实测：用同一镜像起临时容器（`SPRING_PROFILES_ACTIVE` 置空、`JWT_SECRET=reservation-system-jwt-secret-2026`、`KNIFE4J_ENABLE=true`），`/doc.html` 200、`/v3/api-docs` 200；再用默认密钥手工签一个 `role=1` 的 HS256 Token，在 `REDIS_ENABLE=false`（无状态模式）下请求 `GET /api/user/manage` 返回 200 与 5 个用户的列表。

第 5 项有一个容易误判的细节：**Redis 启用时**，`AuthInterceptor` 会校验 Redis 会话，即使签名有效、伪造 Token 也只会得到 401（本次实测）；风险出现在项目明确支持的**无状态模式**（`REDIS_ENABLE=false`）——此时只验签名，默认密钥可直接冒充 admin。加 `prod` profile 后两道防线都在：签名密钥不是默认值，伪造 Token 在两种模式下都 401。

### 回归

```powershell
mvn -f server/pom.xml test                     # 单测 + 集成（含 JwtSecretGuardTest）
pwsh server/scripts/smoke.ps1                  # 41 项接口冒烟（直连 8080，不走 nginx）
cd web; npm run test:e2e                       # 120 例（Vite 5173，不走 nginx）
```

smoke 与 E2E 都不经过 nginx（因此不受网关限流与响应头影响），但都打到容器内 `prod` profile 的 api：浏览器经 Vite `5173` 直连 8080，故 `CORS_ALLOWED_ORIGINS` 必须包含 `5173`，否则登录请求会被 CORS 403（本轮排障实测过这一条）。

## 4. 升级须知

- **存量部署**：拉取本轮代码后，必须在 `.env` 补充 `JWT_SECRET`（至少 32 字节随机值），否则 `docker compose up` 会直接拒绝启动。
- **更换密钥**：所有已签发 Token 立即失效，需重新登录（演示 / 灰度环境可接受）。
- **文档地址**：容器部署不再提供 `/doc.html`；本机 `mvn spring-boot:run` 默认仍可访问，需要时显式 `KNIFE4J_ENABLE=true`。
- **限流阈值**：`rate=10r/m` 适合演示与小规模使用；真实上线应按访问量调整，或把登录限流下沉到 WAF。

## 5. 边界与未做的部分

- 注册接口仍有「开放注册 + 无验证码」的设计（需求未要求），网关限流是唯一约束；如需邮箱/学号校验，属需求变更。
- `CORS_ALLOWED_ORIGINS` 在 compose 下收敛到本机来源（`8088` 部署入口与 `5173` Vite dev / E2E 入口；两者同机、均为回环地址）；若将来绑定域名，需同步更新该变量。
- 看板聚合 SQL 的整段行读取、`(reserve_date, status)` 复合索引未动：前者在当前数据量下无收益，后者属表结构变更，需负责人确认。
