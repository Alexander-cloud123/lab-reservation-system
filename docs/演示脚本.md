## 5. 答辩问答储备

### 5.1 技术栈选型（需求文档四・5 话术）



* **JDK 21 + Spring Boot 3.2.10**：LTS 长期支持版本，Spring Boot 3 全面拥抱 `jakarta.*` 命名空间，虚拟线程（Java 21）为高并发预留能力；选 LTS 保证项目周期内版本稳定、生态成熟，避免答辩被质疑 "用新技术踩坑"。

* **Node 22 + Vue 3.4 + Vite 5**：Vue 3 组合式 API + `<script setup>` 更适合工程化协作；Vite 5 冷启动毫秒级，开发效率高；Element Plus 2.7 与 Vue 3 同源生态，组件一致性最好。

* **为什么不用更重的方案**：需求规模下 Spring Boot + Vue 是 "恰好够用且最稳" 的组合；MyBatis-Plus 减少样板代码、SQL 可控可优化；MySQL 8 窗口函数、JSON 能力满足看板统计。

* **亮点库**：ECharts 5.5（数据看板）、FullCalendar 6.1（日历总览）、EasyExcel 3.3.4（导出）、Hutool 5.8.32（工具集）、Knife4j 4.4.0（接口文档）—— 都是 "在正确的位置引入正确的库"。

### 5.2 冲突检测原理



* 公式：`新开始 < 旧结束 AND 新结束 > 旧开始`，区间重叠判定，覆盖包含 / 部分重叠 / 首尾相接全场景。

* 双重校验：前端提交前实时校验（体验层）+ 后端 Service 层事务内校验（正确性层，同一时段并发提交时由数据库 / 锁保证不会双写）；前后端校验逻辑同公式、同口径（只算已通过）。

* 边界：首尾相接（16:00 结束 = 16:00 开始）不冲突 ——`新开始 < 旧结束` 用严格小于，符合 "前一节结束即可预约后一节" 的业务直觉。

### 5.3 状态流转



* 待审核 (0) → 已通过 (1) / 已驳回 (2)（仅管理员审核触发）；待审核 / 已通过 → 已取消 (3)（用户主动取消，开始前 1 小时可取消）；已驳回 / 已取消为终态。

* 占用计算：仅「已通过」参与冲突与剩余时段计算；待审核 / 已驳回 / 已取消不占名额。

* 表字段：`status` 小整型 + 枚举常量映射，杜绝魔法值。

### 5.4 AI 低耦合可插拔设计（核心加分点）



* **独立&#x20;**`ai`**&#x20;包**：controller/service/dto 全隔离，不侵入预约核心业务；`ai.enable` 关闭后业务链路零 AI 痕迹（实机验证前端入口全隐藏）。

* **双开关**：yml + 数据库双开关，任一处 false 即关闭，部署侧可灰度。

* **60 秒超时降级**：大模型调用超时 / 报错 / 限流 / 无密钥 → 自动切本地规则引擎（推荐打分 / 正则解析 / FAQ 匹配 / 关键词合规），业务不阻断、演示不翻车。

* **密钥安全**：`AGNES_API_KEY` 仅从环境变量读取（`${AGNES_API_KEY:}`），代码零硬编码，前端不直连 AI。

* **只读不写**：AI 全部产物为建议 / 解析结果，写操作必须用户手动确认；生成内容统一标注「AI 生成，仅供参考」。

### 5.5 权限与安全



* **JWT + 拦截器**：登录签发 Token，`AuthInterceptor` 拦截 `/api/**`（放行登录 / 注册），携带 Token 放行；前端 Axios 统一注入 Authorization，401 自动跳登录。

* **密码 BCrypt**：不可逆哈希存储，重置密码默认 123456 也走 BCrypt，管理员无法查看明文。

* **角色鉴权**：学生 / 管理员按角色路由与接口鉴权，管理端接口学生 token 不可访问；前端路由守卫 + 后端拦截双重控制。

* **Token 安全**：JWT 可配置过期；登录会话同时写入 Redis（`auth:token:{userId}`，TTL 与 JWT 一致），退出登录即删除服务端会话、Token 立即失效；同一账号新登录覆盖旧 Token（单点会话）；密码传输走 HTTPS（生产）。Redis 不可用时自动退化为纯 JWT 校验，不阻断登录（详见 5.6）。

### 5.6 Redis 加分项（容器化 / 可注销会话 / 缓存一致性 / 故障降级，需求文档 2.2 第 145 行）

* **为什么用 Redis、怎么部署**：需求文档 2.2 技术栈表第 145 行明确定义的可选加分项，经负责人确认实施。与 MySQL 一致用 Docker 容器 `reservation-redis`（官方 `redis:7.0`，映射 `6379:6379`），启动一条 `docker run -d --name reservation-redis -p 6379:6379 redis:7.0`；客户端用 Spring Boot 默认 Lettuce 客户端（`spring-boot-starter-data-redis`，版本随 parent 管理），未引入 Redisson 等额外组件。

* **无状态 JWT 怎么做到「可注销 / 单点会话」**：纯 JWT 的短板是签发后到期前无法主动作废。本项目登录成功把 Token 存进 Redis（Key 固定为 `auth:token:{userId}`），拦截器在 JWT 验签、账号状态校验通过后，再查 Redis 比对当前会话——① 退出登录删除该 Key，旧 Token 立刻 401；② 同一账号再次登录覆盖该 Key，旧设备 Token 立刻失效，实现「单点会话」；③ TTL 与 JWT 24h 一致，到期自动清理，不产生垃圾 Key。

* **缓存了什么、怎么保证一致性**：只缓存两类「高频读、变化慢」的数据——数据看板三个聚合统计（缓存 60s）与学生端教室列表（短缓存 60s，「今日剩余时段」等动态数据不做长缓存）。采用「写后失效（Cache-Aside）」：预约提交 / 审核 / 批量审核 / 取消、教室增改 / 启停 / 删除后，用 SCAN 主动删除对应缓存 Key，下次请求回源重建，保证核心数据一致；Key 带查询参数指纹，不同筛选条件互不串缓存。

* **Redis 挂了会不会全站崩**：不会，这是重点讲解点。`redis.enable` 一键启停；RedisCache 封装层对每个操作 try-catch，连接失败 / 命令超时（配置 3s）时——登录照常签发 JWT（退化为无状态校验）、拦截器退化为仅 JWT 放行、查询接口直接回源查库，接口行为与平时完全一致，日志打印降级告警；容器重启后自动恢复缓存。即「Redis 只做加速与会话增强，绝不做持久化依赖」，设计风格与 AI 模块超时降级一致。

* **现场可演示的命令**：`docker exec reservation-redis redis-cli ping`（PONG）、`keys 'auth:token:*'`（看登录会话）、`keys 'cache:*'`（看业务缓存）；`docker stop reservation-redis` 后页面照常使用 = 故障降级，`docker start` 后恢复。

### 5.7 其他可能追问



* **批量审核一致性**：后端逐条校验状态（仅待审核生效），事务内处理，返回成功条数。

* **导出实现**：EasyExcel 按当前筛选条件查询后写入，文件名含时间戳。
