# 可靠性验证（故障演练 · 性能基准）

> 目标：把《需求设计文档》§1.5 的非功能指标从「文档声明」变成「可复现的实测证据」。
> 对应条款：响应时间 —— 普通页面加载 ≤2s、冲突检测查询 ≤500ms、AI 接口响应 ≤60s。
> 本文件只覆盖**接口/页面层**；并发正确性由 `server/src/test/java/com/example/reservation/concurrency/ConcurrencyIntegrationTest.java` 覆盖，AI 60s 由 `server/scripts/ai-real-acceptance.ps1` 与降级单测覆盖（本轮未重复执行，免费额度紧）。

## 2. 故障演练（Redis / MySQL 不可用）

### 2.1 运行方式

```powershell
# 需要 compose 栈已启动；演练会真的 stop/start redis 与 mysql，仅限本机开发栈
pwsh server/scripts/chaos-drill.ps1              # 15 项断言
pwsh server/scripts/chaos-drill.ps1 -IncludeSlow # 额外验证会话撤销的 60s 快照窗口（17 项）
```

脚本在 `try/finally` 中恢复服务，结束时校验四服务 healthy 与 `13 / 5 / 12` 数据不变；任一项失败退出码 1。

### 2.2 实测结果

| 场景 | 期望语义 | 实测 |
|---|---|---|
| Redis 停机：带合法 Token 访问 `/api/user/info` | 会话中心不可用 → fail closed，不放行数据 | **HTTP 401，`code=401`「登录已过期」**，耗时 **9 s**（Lettuce 重试放大，不是瞬时） |
| Redis 停机：`POST /api/user/login` | 不阻断登录（失败计数降级到内存兜底），但必须受超时约束、不泄露堆栈 | **HTTP 200，`code=200`，耗时 12.1 s**（降级放行） |
| Redis 停机：降级期间签发的 Token 访问受保护接口 | 会话中心缺失 → Token 不可用 | **401** |
| Redis 恢复 | `PONG` 后接口自愈 | PONG **1.1 s**；受保护接口恢复 **200**，自愈耗时 **10.9 s**（脚本给 30 s 窗口，Lettuce 重连 + 会话重建可能更慢） |
| MySQL 停机：`GET /api/classroom/list` | 统一错误包、不泄露堆栈、不无限挂起 | **HTTP 200 + `code=500`「系统异常，请稍后重试」**，耗时 **30 s**（Hikari 连接等待上限） |
| MySQL 停机：`POST /api/user/login` | 同上 | **HTTP 200 + `code=500`**，耗时 **30 s** |
| MySQL 恢复 | healthcheck healthy 后列表恢复 | healthy **5.3 s**；列表 **200，total=12**，耗时 **0.02 s** |
| 会话撤销（`-IncludeSlow`） | Redis 用户快照 TTL=60s：窗口内旧 Token 仍可用，窗口外必须失效 | 窗口内 **200**；65 s 后 **401** |
| 演练结束 | 服务与数据完全恢复 | 四服务 healthy；预约 13 / 用户 5 / 教室 12 |

### 2.3 从演练中确认的三件事

1. **会话中心故障是 fail closed 的**：Redis 不可用时业务接口一律 401，不会因为「拿不到会话」而放行请求；这是与安全基线配套的正确姿态。
2. **数据层故障是「有界失败」**：MySQL 不可用时返回统一错误包而不是空白页/堆栈，最多等 30 s（Hikari `connection-timeout` 默认值），不是无限挂起。
3. **恢复需要时间**：Redis 重启后 Lettuce 重连 + 会话重建需要约 10–30 s，期间仍 fail closed。运维上意味着「Redis 恢复 ≠ 立即恢复服务」，重启窗口内用户会看到 401 并需要重新登录。

> 注意：项目统一用 HTTP 200 承载 `Result` 包（`code` 才是业务结果），因此故障期间接口的 HTTP 状态码仍是 200；判定必须看 `code` 与 `message`，不能用 `curl -f` 这类只看状态码的脚本做健康检查。

## 3. 接口性能基准

### 3.1 运行方式

```powershell
# 仓库根目录执行；直连 api（8080），不经 nginx
node web/scripts/bench-api.mjs --samples=50 --rounds=3 --flush-stats --out=.devtmp/bench/report.md
```

口径：每接口先预热 5 次，再采样 3 轮 × 50 次，取各百分位的**中位数**；冲突检测按 500 ms 阈值判定，超阈退出码 1。`--flush-stats` 会在每次采样前清空 `cache:stats:*`，得到「逐次冷缓存」的成本。

### 3.2 实测结果（2026-11-15）

| 接口 | 样本 | p50 (ms) | p95 (ms) | p99 (ms) | max (ms) | 判定 |
|---|---:|---:|---:|---:|---:|---|
| 冲突检测 `/api/reservation/conflict` | 150 | 15.3 | 16.5 | 17.3 | 17.3 | **PASS（≤500ms）** |
| 教室列表 `/api/classroom/list` | 150 | 3.4 | 4.4 | 5.4 | 5.4 | - |
| 我的预约 `/api/reservation/mine` | 150 | 5.1 | 6.6 | 7.4 | 7.4 | - |
| 日历总览 `/api/reservation/calendar` | 150 | 3.9 | 5.8 | 8.0 | 8.0 | - |
| 审核列表 `/api/reservation/manage` | 150 | 4.8 | 5.9 | 6.5 | 6.5 | - |
| 看板概览 `/api/stats/overview` | 150 | 4.3 | 5.0 | 5.3 | 5.3 | - |
| 看板使用率 `/api/stats/usage-rate`（冷缓存，逐次清理） | 50 | 5.3 | 7.4 | 11.7 | 11.7 | - |
| 看板使用率 `/api/stats/usage-rate`（热缓存） | 150 | 2.9 | 3.7 | 4.1 | 4.1 | - |

结论：

- **冲突检测 p95 ≈ 16.5 ms**，相对 500 ms 上限有约 30 倍余量；该接口是纯查询（按 `classroom_id + reserve_date` 索引 + 时间重叠条件），在 13 条种子数据下未观察到抖动。
- **统计接口冷/热差约 2 倍**（p95 7.4 → 3.7 ms）：缓存回填确实生效，但数据量只有 13 条时收益绝对值很小；数据量上去后用 `--flush-stats` 复跑即可观察真实差距。
- 其余列表接口 p95 均在 10 ms 以内；`stats-overview` 未走缓存（聚合计算是直查），因此未做冷/热对比。

口径：Playwright Chromium 1440×900，**真实界面登录**后复用会话；每页从 `goto` 到「首屏关键元素可见」计时（含网络、JS 执行与组件渲染），命中 nginx 托管的构建产物（`web` 容器 8088，gzip 已开）。

## 5. 已知边界

| 边界 | 说明 |
|---|---|
| Redis 停机时登录可成功、但 Token 不可用 | 登录锁计数有内存兜底，会话校验没有；因此「能登录但立刻 401」是 fail closed 的副作用。前端只会收到 401 并提示重新登录，不会出现放行。 |
| 恢复期 10–30 s 的 fail closed | Redis 重启后 Lettuce 重连 + 会话重建需要时间，期间所有受保护接口 401。可用「重启前先摘流量」或「恢复后重新登录」缓解，属运维取舍，本轮未改代码。 |
| MySQL 故障 30 s 才返回 | 来自 Hikari `connection-timeout=30s`。若希望更快失败可调小（属配置取舍，本轮未改）；30 s 内请求线程会被占用，高并发下需要配合熔断，当前项目未引入（避免超出技术栈）。 |
| 会话撤销有 ≤60 s 窗口 | `cache:user:state:*` TTL=60s，`token_version` 变更在缓存过期后才生效；`-IncludeSlow` 已实测。 |
| 单客户端、本机回环 | 无并发压力、无网络延迟与带宽限制；不能据此推断生产容量。 |
| 数据量 13 条 | 索引与缓存收益有限；缓存命中率、分页性能需真实数据量复测。 |

## 7. 已知的设计取舍（为什么不是更强的方案）

- **没有引入 Actuator / Prometheus**：需要新增 starter 依赖，超出《需求设计文档》技术栈边界；当前用脚本 + 日志 + 现有 Redis 缓存即可拿到本轮需要的证据。
- **没有做压测**：需要造数（会涉及表结构与索引变更），且收益主要在「容量叙事」；本轮先证明需求下限。
- **没有把故障演练放进 CI**：它需要控制 Docker 停止/启动服务，在 CI 中会互相污染且耗时；定位是「发布前/本地手动执行」的卡口，脚本保持与 `security-check.ps1` 同风格。
